# 제출물 기반 이해도 모의시험
실제 문항을 미리 모르는 상태에서 준비하고, 코드·문서·AI 없이 답하는 연습이다. 다음 시험의 실제 규정은 현장 공지를 우선한다.

## 구현을 끝낸 뒤 15분
1. 필수 구현·검증·제출 절차 시간을 먼저 확인한다. 15분은 훈련 기본값이며 공식 시험 시간이나 충분한 이해를 보장하는 수치가 아니다.
2. AI에게 현재 프로젝트의 `prompts/4-essay-practice.md`를 읽고 실행하게 한다. bootstrap으로 복사했다면 `hackathon-notes/prompts/4-essay-practice.md`다.
3. '15분 훈련 시작'이라고 요청하고 타이머를 켠다. 자료 재확인과 사용자 답변 시간도 15분에 포함한다.
4. 0~4분에는 핵심 설명을 듣고, 4~11분에는 자료를 덮고 답변·교정을 반복한다. 11~15분에는 약한 부분의 변형 질문에 도움 없이 답한다.
5. 종료 시 유형별 상태와 남은 오해를 확인한다. 읽기만 한 항목, 묻지 못한 항목을 이해 완료로 표시하지 않는다.

AGREEMENT는 목표 확인 자료다. 실제 동작·검증 범위는 최종 코드와 실행 기록, 선택 이유와 판단 과정은 당시 기록에서 확인한다.
기억할 핵심은 '설계 선택 / 데이터 흐름 / 구현 범위 / 실패 동작 / 검증 한계 / AI 협업' 여섯 가지다.

## 출제 기준
고정 문항의 답을 외우는 대신 현재 제출물에서 중요한 결정과 취약점을 찾아 질문한다. 아래는 출제 틀이며 실제 출제 예측이나 정답이 아니다.

| 유형 | 실제 제출물로 바꿔 물을 질문 |
|---|---|
| 설계 선택 | 핵심 판단 방식은 왜 선택했으며, 대안과 비교해 무엇을 포기했는가? 작은 예제로 차이를 설명하라. |
| 데이터 흐름 | 입력 한 건이 검증·처리·저장·화면까지 어디를 거치는가? 각 모듈의 책임과 상태 소유자는? |
| 구현 범위 | 실제 구현·검증한 것과 미검증·설계·미구현은? 다른 평가자가 무엇으로 재현하는가? |
| 실패 동작 | 잘못된 입력이나 처리 중 데이터 변경 시 기존 데이터·결과는 어떻게 되는가? 남는 위험은? |
| 검증 한계 | 자동 테스트가 놓친 가정은? 경계값·반례·제약 변경으로 무엇을 추가 확인할 것인가? |
| AI 협업 | 실제 오류에서 AI 제안을 어떻게 채택·수정·거절했는가? 누가 어떤 근거로 판단했고 재검증 결과는? |

AI가 통과했다고 말한 사실만으로 실행 근거가 되지 않는다. 자동 테스트와 브라우저 확인의 범위를 구분한다.
사용자 판단이 기록에 없으면 '확인 필요'라고 답하며, 실제 하지 않은 판단이나 테스트를 꾸미지 않는다.

## 반복 연습과 판정
- 짧은 답변은 '결론 → 이유 → 코드·실행 근거 → 한계' 순서로 연습한다. 모르는 부분은 모른다고 밝힌다.
- 한 문항씩 답한 뒤 틀린 부분만 설명받고, 입력·제약·실패 시점을 바꾼 질문에 다시 답한다.
- 상태: 미질문 / 미이해 / 도움 필요 / 독립 설명 / 변형 확인. 근거가 없으면 별도로 근거 부족을 표시한다.
- 힌트 없이 정확히 설명하면 독립 설명, 새 조건에서도 이유와 결과를 설명하면 변형 확인이다. 공식 점수나 합격 기준은 아니다.
- 사전 연습에서는 시간을 늘려 약한 부분을 반복할 수 있다. 현장에서는 정해진 시간에 멈추고 미이해 항목을 남긴다.
- 작은 코드 수정 과제는 추가 연습 시간에만 한다. 기본 15분에 구현 작업을 끼워 넣지 않는다.

## 기본 웹 부품으로 해보는 추가 연습
아래는 키트 예제 앱을 익히는 용도다. 실제 제출 프로젝트의 기능·약점으로 오인하지 않는다.
자료·코드·AI를 보지 않고 답한 뒤에만 아래 채점 기준을 확인한다.
1. 등록 버튼에서 파일 저장까지 흐름을 파일/함수 이름으로 설명하라.
2. 브라우저 min=0이 있는데 왜 서버도 음수를 거부하는가?
3. 동시에 등록한 두 항목 중 하나가 사라지는 문제를 이 코드는 어떻게 줄이는가?
4. 손상된 저장 파일이 발견되면 빈 배열로 자동 초기화하면 안 되는 이유는?
5. 이 앱의 가장 큰 운영상 약점 2개를 '약점 → 파급 → 개선'으로 설명하라.

### 직접 수정 과제 (별도 추가 15분)
'완료 항목은 value 변경 불가, 대기로 되돌린 뒤 수정 가능' 규칙을 추가하라.
규칙을 순수 함수로 분리하고 정상/거부/복구 후 수정 테스트를 작성하라.
UI에 값 편집이 없으므로 API 테스트로 검증하거나 필요하면 편집 화면을 추가한다.
왜 서버 규칙이 필요한지 설명하라.

### 예제 채점 기준 (5문항 × 4점)
각 문항: 현재 동작 1점, 코드 근거 1점, 깨질 조건 1점, 검증/개선 1점.
1: app.js→POST→body/validateItem→store.change→파일 교체→refresh.
2: 직접 API 요청은 HTML 제약을 우회함. 음수 요청 400으로 검증.
3: 읽기-수정-저장을 큐로 직렬화. 다중 프로세스/서버에는 미적용.
4: 손상을 빈 데이터로 취급하면 다음 저장에서 기존 데이터 유실. 오류·백업·복구가 필요.
5: 인증 없음, 단일 JSON/프로세스, 가져오기 중복 등 실제 한계와 영향·대안을 연결.
준비용 자가 기준: 16점 이상 + 수정 과제 완료. 공식 평가 기준이 아니다.
