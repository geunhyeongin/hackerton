# 웹 구현
README/AGENTS/공개 테스트와 합의문부터 읽어. 기존 실행 구조를 우선해.
Node 기반 새 앱이 허용되면 web-workbench를 검토하고 필요한 부품만 사용해.
도메인 규칙은 순수 함수, UI는 입력·로딩·빈 상태·오류·결과, 서버는 타입 검증·외부 제한시간·저장 실패를 처리해.
한 흐름을 브라우저에서 먼저 완주하고 나서 기능을 늘려.
설명하기 어려운 추상화·불필요한 프레임워크·다중 에이전트 의존성을 추가하지 마.
각 변경 후 내가 알아야 할 함수/이유/실패 조건을 3줄로 남겨.

## 구현 중 복습 근거 준비
구현과 필수 검증을 우선하고, 매 변경마다 나에게 설명 시험을 요구하며 멈추지 마.
기존 HANDOFF.md의 '자료 없이 답하기 위한 복습 근거'를 중요한 결정·오류 해결·검증 후 짧게 갱신해.
HANDOFF-RULES.md와 양식을 따르고, 다음 여섯 항목에 실제 파일/함수와 실행 기록을 연결해.
- 설계: 선택 / 이유 / 대안 / 포기한 것. 코드에서 추정한 이유는 'AI 추정', 내가 확인한 이유는 '사용자 확인'으로 구분.
- 흐름: 실제 입력 한 건 → 검증 → 계산/판정 → 결과 검증(있다면) → 저장 → 재조회/화면. 각 책임과 상태를 가진 곳.
- 범위: 구현·검증 완료 / 구현했지만 미검증 / 설계·가정 / 미구현. 테스트가 있다는 것과 실행했다는 것을 구분.
- 실패: 잘못된 입력·외부 실패·처리 중 데이터 변경 시 기존 데이터와 결과가 어떻게 되는지. 미지원·미확인은 그대로 표시.
- 검증 한계: 통과한 검사가 보장하는 범위 / 놓친 가정 / 작은 반례나 경계값 / 추가 확인 방법.
- AI 협업: 증상 → AI 가설·제안 → 실제 채택·수정·거절 → 판단 주체·근거 → 수정 위치 → 재검증 결과.
AI가 독자적으로 한 수정은 그렇게 적어. 내가 하지 않은 판단·거절이나 실행하지 않은 테스트를 만들지 마.
사용자 판단 근거가 기록에 없으면 '사용자 판단 확인 필요'로 남겨. 시크릿과 실제 업무 데이터는 기록하지 마.
완료 시 최종 코드와 복습 근거를 대조하고 낡은 설명을 고쳐. 핵심 알고리즘은 손으로 따라갈 작은 입력과 결과를 준비해.
그다음 이해도 연습 프롬프트(원본 prompts/4-essay-practice.md, 복사본 hackathon-notes/prompts/4-essay-practice.md)를 안내해.
15분 훈련은 내 시작 요청 후 진행하며 필수 검증·제출 절차 시간을 임의로 줄이지 마.
